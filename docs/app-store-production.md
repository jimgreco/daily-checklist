# Production App Store Release

The Release workflow (`.github/workflows/release.yml`) runs `verify.yml` (server tests, dependency audit, container build, Playwright browser journeys, iOS unit tests) on pull requests and pushes to `main`. Main pushes then deploy the server and run the guarded iOS TestFlight path using existing signing assets. The uploaded build is App Store-eligible (`buildAudience` in `.github/scripts/release-policy.json`): it is distributed only to the approved internal TestFlight group and can be selected for App Store review. Submitting for review stays manual.

A manual Release run on `main` verifies, then releases what its checkboxes select:

- `server` (default true): deploy the server without a push, for example to redeploy an exact SHA with existing pinned SSH trust. This replaces only the existing `daily` service and preserves its effective runtime configuration. See [isolated server release](server-release.md).
- `ios` (default true): validate the pinned existing profiles without changing Apple resources, archive the app, and upload an App Store-eligible build to TestFlight for the approved internal group (iOS tests run first in verify). See [existing-assets-only release](native-testflight-existing-assets.md). A successful upload does not mean an App Store release or device acceptance.

App Store listing, screenshot and review submission are in the separate manual-only App Store workflow (`.github/workflows/app-store.yml`). For a release-candidate build, set these inputs there:

- `update_app_store_metadata`: `true` when `fastlane/metadata` should replace the editable App Store Connect listing fields.
- `update_app_store_screenshots`: `true` when screenshots should be regenerated from deterministic UI-test data and uploaded to App Store Connect.
- `app_store_version`: leave blank unless App Store Connect has an editable version that differs from Xcode `MARKETING_VERSION`.
- `screenshot_devices`: keep the default unless Apple requires another iPhone screenshot size.
- `submit_for_review`: `true` attaches `review_build` (the exact uploaded build number) to the editable App Store version, uploads the source-controlled metadata, answers export compliance (standard encryption only), IDFA (not used) and third-party content (none), and submits it for review. `review_release` chooses whether Apple's approval releases it automatically or waits for a manual release.

## Automated Fields

Fastlane uploads these fields from `fastlane/metadata`:

- name
- subtitle
- promotional text
- description
- keywords
- support URL
- marketing URL
- privacy URL
- release notes
- copyright

Fastlane uploads screenshots generated by the `DailyScreenshots` UI-test target. Screenshots use debug-only seeded local data and do not require a production account.

## Manual App Store Connect Setup

Apple still requires some one-time or review-specific fields in App Store Connect:

- create the app record for bundle ID `com.jimgreco.dailychecklist`;
- set age rating;
- set category and content rights;
- set pricing and availability;
- complete App Privacy answers using `docs/app-store-privacy.md`;
- fill review contact information;
- fill demo account notes if Apple requests credentials;
- choose the uploaded build and submit for review (or use the `submit_for_review` input above).

Ritual Cue sets `ITSAppUsesNonExemptEncryption` to `false`, so the export-compliance answer should match standard platform encryption only.

## Local Screenshot Review

Use Ruby 3.3 or newer, matching the GitHub Actions workflow.

```sh
bundle install
bundle exec fastlane ios screenshots
open fastlane/screenshots
```

To upload reviewed screenshots manually:

```sh
APP_STORE_CONNECT_KEY_ID=... \
APP_STORE_CONNECT_ISSUER_ID=... \
APP_STORE_CONNECT_API_KEY="$(cat AuthKey_XXXXXX.p8)" \
bundle exec fastlane ios screenshots_and_upload
```
